# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

A pipeline that normalizes pipeline-valve attribute values (from an Excel sheet) against technical rules extracted from the API-600 standard, exposed through a chat-like web UI. It is built on **LangGraph** state machines on the backend and a **React (create-react-app)** frontend.

## Repo layout

- `graphs/rag_agent/` — the **runtime** RAG pipeline: a FastAPI app (`api.py`) wrapping a LangGraph `StateGraph` that normalizes each row of an uploaded Excel file using rules retrieved from a vector store. `api.py` holds only the endpoints and the chat glue. The pipeline itself lives in `graphs/rag_agent/pipeline/`, one module per layer, each importing only from the layers before it: `common` (logger, attribute/phrase matching) → `answers` (parsing the model's answer, the "applied" text) and `subjects` (item kind, equipment class, scope) → `deterministic` (exclusions, phrase/synonym tables, roots, closed registers) → `retrieval` (`build_rules_text`, class block, clauses and tables pulled by reference) → `guards` (`_rejection_reason` and the other checks on an answer) → `normalizer` (tool loop, normalize + verify, voting) → `postprocess` (column passes) → `frames` / `graph` (`start_row`, `normalize_row`, `run_single_rule_set`) → `user_rules` → `excel` / `runner` (`normalize_table`). Names the eval scripts use (`api.run_single_rule_set`, `api.prepare_frame`, `build_rules_text`, …) are re-exported from `api.py`. Function names below refer to these modules.
- `graphs/structured_documents/` — an **offline/one-time** extraction pipeline that turns the `API-600.pdf` standard into structured `rule_groups.json` (rules grouped by attribute). It is not served; it runs as a standalone script.
- `client/` — React frontend (chat UI) that uploads an Excel file to the backend and downloads the normalized result.
- `venv2/` — the Python virtualenv with the full backend stack (fastapi, openpyxl, sentence-transformers, pytesseract, langgraph). Use it for all backend commands. (`venv/` is an incomplete second env — don't use it.)

## Commands

All commands run from the repo root unless noted.

```bash
# Backend (FastAPI on http://localhost:8000)
venv2/Scripts/python -m uvicorn graphs.rag_agent.api:app --reload --port 8000

# Frontend (dev server on http://localhost:3000)
cd client && npm install && npm start

# Offline PDF -> rule_groups.json extraction (runs the graph on import)
venv2/Scripts/python -m graphs.structured_documents.structured_documents_graph

# Tag which product/assembly each rule group governs (subjects.json).
# Part of the extraction graph, but also runnable on its own over existing rule_groups.json:
venv2/Scripts/python -m graphs.structured_documents.subject_tagging

# Regression eval of the normalization pipeline (calls the LLM, ~2 min)
venv2/Scripts/python -m graphs.rag_agent.eval.run_eval
venv2/Scripts/python -m graphs.rag_agent.eval.run_eval --rows 6,8,9 --tag alloy

# Frontend tests (react-scripts / jest)
cd client && npm test                 # watch mode
cd client && npm test -- --testPathPattern=MessageInput   # single test file
```

There are no unit tests on the Python side; `graphs/rag_agent/eval` is the regression check for the normalization pipeline (it costs LLM calls, so run it deliberately). The `structured_documents_graph` module executes the full pipeline at import time (its bottom line calls `graph.invoke(...)`), so running it has side effects.

## Architecture & data flow

There are two separate LangGraph graphs with a shared data artifact between them.

### 1. `structured_documents` — builds the rule knowledge base (offline)

`graphs/structured_documents/structured_documents_graph.py` defines a linear `StateGraph`:

`first_node` → `formatting_text_node` → `grouping_rules_node`

- `first_node` renders each PDF page to an image (PyMuPDF `fitz` + Tesseract OCR for orientation) and sends it to a local Qwen3-VL vision model (`vlm`) to extract structured blocks (paragraphs/headings/tables). The VLM sits behind an ngrok tunnel that drops in the middle of long documents, so each page call is retried (`_invoke_vlm`, up to `VLM_ATTEMPTS` with growing pauses, about half an hour in all) and every finished page is saved to `pages_data.partial.json`; a rerun resumes with the pages still missing instead of re-reading the document. Pages are independent and are read `VLM_WORKERS` at a time (env, default 4; `_read_page`), so the server must accept as many sequences (`--max-num-seqs` of vLLM): with one request at a time the two GPUs sat idle decoding a single page. They finish in any order, so the partial file is keyed by `page_number` and sorted at the end. Before this, a drop on page 80 of 82 lost the whole run. Model, URL and token limit come from `Settings` (`VL_model`, `VL_url`, `VL_max_tokens`); the full `Qwen/Qwen3-VL-8B-Instruct` reads pages without the losses of the earlier 4-bit build (half of an OGS-STD-001 page with seven general rules was skipped, table rows of EMD-SPEC 700 merged across tables). Letters that look the same in Latin and Cyrillic (`C`/`С`, `A`/`А`) cannot be told apart on an image. A table at the top of a page with no caption of its own is the continuation of the previous page's table: both VLM builds used to skip its rows or give it the next table's caption (EMD-SPEC 700 lost `Ball mounting` and part of the materials that way), and `VL_prompt` now says to transcribe it with an empty title. Told that, the VLM sometimes writes every caption of the page as a separate heading block above an untitled table; `block_grouping.parse_page_content` (the one reader of page JSON) gives such a table the heading right above it as its title (`_attach_captions`) — a continuation at the top of a page sits under a running header paragraph, not a heading, and stays untitled.
- `formatting_text_node` uses `gpt-4o` to validate/repair table cells and merge paragraphs broken across page boundaries. Page JSON is read through `block_grouping.parse_page_content`, which also repairs escapes JSON does not allow (the VLM writes feet as `\'`); a page the check returns broken (truncated JSON, no blocks) is replaced by the VLM page. Before that, one bad escape printed `error pass`, and the page silently vanished from the grouping.
- Grouping (`GROUPING_MODE=blocks`, `block_grouping.py`): the model only assigns block ids to groups, and the text is copied verbatim. `build_units` treats a heading that starts with a clause number `x.y` and is full text (over 80 characters or ending with a full stop) as a clause, not as a section title. The VLM marks whole rule clauses as headings ("11.4 Valve operators are written Handwheel, with 'HW'…"), and as titles their text never reached the rules: PQS-STD 330 lost 31 clauses (68/108 → 99/108 once fixed), EMD lost 6, including `8.6 Metric thread`. A document whose block text exceeds `WINDOW_CHARS` is grouped in windows cut at section boundaries. Each window sees the names of the groups created so far, and blocks left unassigned get one final pass against all groups. A single call over an 82-page document put all 2270 blocks into `Global`. A document with its own section per equipment class gets one group per class (`kind="class"`: definition, the class's attribute table, the clauses of that section). Before this group kind existed, those sections landed in `Global`, and every row of EMD-SPEC 700 carried all ~50 class descriptions. The prompt forbids putting identity matrices and worked examples in a class group, and forbids class groups when the document has no per-class sections. Without that restriction, OGX-STD 410 got "classes" built from its identity matrix, took the material examples out of the material group, and its `25Cr-20Ni` broke.
- `grouping_rules_node` groups rules by attribute and **appends** them to `graphs/structured_documents/data/output/rule_groups.json` (it loads existing groups first, then re-saves — accumulation, not replace).
- `subject_tagging_node` (`subject_tagging.py`) writes `subjects.json`: which product or assembly each group governs. It matters only for a document that covers more than one subject, where the same attribute name means different things; both current documents come out as a single subject (`gate valve`), so the runtime filter below is inert for them. The step is optional — if it fails or the file is missing, everything behaves as before.

- `rule_cards_node` (`rule_cards.py`, also runnable alone: `venv2/Scripts/python -m graphs.structured_documents.rule_cards --doc <folder>`) writes `rule_cards.json`: the model restates the global rules and each presentation group once, as an unambiguous card (written form, unit/decimals, values and whether the list is closed, accepted forms → written form, steps, exceptions, what the text leaves open). An accepted pair is kept only if both its form and its written form appear literally in the document text, so the model cannot invent a mapping. At runtime `RULE_CARDS` picks how the cards are used (`pipeline/deterministic.py`). The default is `forms`: `_apply_card_forms` (step 0.6 of `apply_deterministic`) replaces an accepted form with the written form, but only where that written form is one of the card's own `values`. This covers accepted forms stated in prose ("pipe is Seamless (‘SMLS’ and ‘S/L’ accepted)"), which the model had read now as "replace", now as "keep". Measured on MNT-DN-014 and EMD: 61 rows closed, 0 wrong, MNT 94 → 95, about 29% fewer model calls. Cards also carry `examples` (the document's before → after pairs, both sides verbatim and grounded in the text) and `unit_spacing` (the document requires a space between number and unit, forbids one, or says nothing). The checks read these instead of searching the rule text with regexes: `guards._examples_in` returns the card examples that appear in a row's prompt, for `_example_leak`, `_relabel_sanctioned` and `_example_keeps_space`, and a group's value shapes (`retrieval`, value-shape fallback) come from its card examples. `_document_mandates_spacing` reads `unit_spacing`. The card examples cover more than the regexes found (OGX 32 against 16, XYZ 205 43 against 36). A handful the model left out (TPX `Ni625-Cr21 → 21Cr-625Ni`) are a known gap. The global card also records `trailing_zeros`. It is `remove` only when the general rules say so (EMD 7.3, MNT "No trailing zeros") and actually mention zeros; then `guards._drop_trailing_zeros` strips them from the model's answer (`50.0 kg` → `50 kg`, `0.00 to 0.25 bar` → `0 to 0.25 bar`), leaving numbers inside designations (`B16.10`) alone. The model had read "round to one decimal" as "show one decimal". Documents that want fixed decimals (`0.630 in.`) are left untouched. `on` / `compact` also put the cards into the prompt (`compact` in place of the raw text), and both made things worse: the restatement dropped nuance ("2 decimal places" where the document meant "at most two") and the model trusted it over the source — MNT 94 → 90–92, EMD 95 → 88–93.
- `table_roles_node` (`table_roles.py`) writes `table_roles.json`: the role of every list of value pairs in each group's text (closed register of codes, synonyms, conversion factors, examples, other). The runtime builds its closed registers and synonym lists from it — see `_load_table_roles` below.

Config for this graph lives in `graphs/structured_documents/modules/config_structured_documents_graph.py`, which holds all prompts and paths. Which PDF to extract is taken from `STRUCTURED_DOC_PATH` when that variable is set, so another document can be run without editing the file: `STRUCTURED_DOC_PATH=graphs/structured_documents/data/input/<file>.pdf venv2/Scripts/python -m graphs.structured_documents.structured_documents_graph`. It hardcodes a Tesseract binary path (`C:\Program Files\Tesseract-OCR\tesseract.exe`), a local `SentenceTransformer` model (`all-MiniLM-L6-v2`), and an ngrok-hosted VLM endpoint — these are environment-specific and may need changing.

### 2. `rag_agent` — the runtime normalization API

`graphs/rag_agent/modules/config.py` is the entry point for app config:

- `load_all_rule_sets()` scans `structured_documents/data/output/*/rule_groups.json` and builds one `RuleSet` per document: global rules, local rule groups (name + aliases + body), a semantic index, a BM25 index, and the sidecar files of that document's folder (`deterministic_rules.json`, `phrase_rules.json`, `*_attributes.json`, `excluded_attributes.json`, `render_templates.json`).
- `load_vector_store()` caches each document's index in `data/input/vector_store_<doc>.json`. **Delete that file to force regeneration** after changing the rules of a document.
- `_build_closed_registers()` turns "phrase → code" pairs into closed registers, keyed by code prefix. A pair whose phrase names its own attribute (`Pump size` in the group `pump size`) is a keyword→root pair and is kept out of the registers — `deterministic_order.json` says so when the extraction produced it, `_names_its_attribute()` when it did not, and without that `Pump size 4` normalized to the bare root `PS`; `_attribute_to_register_from_origins()` maps an attribute to its register(s) from where each phrase was extracted. A pair counts as a register entry (not a keyword→root pair) when the phrase is multi-word or the code carries a digit/separator (`_is_register_pair`).
- What a list of value pairs in the rules *means* is decided by the model once, at extraction (`graphs/structured_documents/table_roles.py`, node `table_roles_node`, also runnable alone: `venv2/Scripts/python -m graphs.structured_documents.table_roles --doc <folder>`). It reads each group's text — a list may be a table, `col: 'v'` lines, `|` columns, `A -> B` lines or prose — and gives every list a role: `register` (name → code, a value outside it is unregistered), `synonyms` (accepted form → written form, not exhaustive; also one designation system → another, `DN 250 → NPS 10`), `conversion`, `examples`, `other` (allowed values without codes, attribute indexes, other names of the attribute or item, abbreviation glossaries). Pairs are kept only if both sides literally appear in the group text. `config._load_table_roles` turns `table_roles.json` into the closed registers and the synonym lists; a global group's list counts only when the model marked it `any_attribute`. This replaced `_extract_table_pairs` (regexes over rule lines, guessing the code column by the look of a cell) and the header-based synonym detection: on OGS-STD-001 they made a register of the unit-conversion factors (`GPM (US): 'x 0.2271' → M3/H`) and of test-example rows (`4.5 in → R-SB-02`), so every flow, length and range got «pending registration», and missed the material synonym table whose forms stood in the FIRST column. A document without `table_roles.json` has no registers or synonym lists from its text — run the step for it.
- `modules/tables.py` indexes the document's tables straight from `data_after_check.json` (number → rows; an untitled table with the same columns continues the previous one), so a reference (`Table X.Y`) can be quoted into the prompt (`_table_blocks`). `_link_cited_lists` also gives a synonym list whose title carries a table number to the groups citing it and to attribute-index rows naming an attribute (`Attribute: 'Roof type'; Written form: 'Canonical value of Table 12.41'`). At runtime `_apply_synonyms` (step 0.5 of `apply_deterministic`) replaces an exact form (case-insensitive) with its written form; a form that leads to two written forms within a list is dropped; a miss is not "pending registration" — the row goes to the model.
- `_render_templates_from_rules()` rebuilds a render template from the document's own units table (`Temperature — Unit: degC; Decimals: 1`) when the extraction produced none, and only when the line's label names the group — a table written per equipment class says nothing about one attribute. Without it, rounding a value already in the right unit was left to the model, which read "already in the prescribed form" and changed nothing. `_match_render_template` then picks, among the retrieved groups' templates, the one whose unit matches the value's own: the first retrieved group is often another quantity. Without it such an attribute has no closed register at all and the model picks the code from prose — which is how a code that exists in no table (`FLG-RTJ`) got invented.
- `hybrid_search()` merges semantic and BM25 hits via RRF and drops groups below `min_score`. `build_rules_text()` then force-includes the group whose name or alias *is* the row's attribute: ranking is a similarity guess, an equal name is not, and without it `IP rating: IP 54` reached the model with four other groups and no IP rule.
- `_build_clause_index()` maps a clause number to its text across the whole document, so a rule that says "see 13.1" can have 13.1 pulled into the prompt even when that clause sits in a group the retrieval did not select.
- `build_app_config()` assembles `AppConfig` (settings + rule sets + chat model) and is cached via `lru_cache` in `api.py`.

`graphs/rag_agent/api.py` exposes three endpoints. `POST /chat` is what the UI talks to: multipart `message` / `history` / `standards` (the names the user picked, empty = all) / `session_id` / optional `file`. It runs the agent (see below) and answers with `{reply, session_id, files}`, where each produced file is base64 inside the JSON, so one round trip carries both the answer and the files. `GET /standards` lists the loaded documents (`name` + a readable `label`) for that picker. `POST /process` accepts an uploaded `.xlsx` with `Attribute`/`Value` columns and returns a result `.xlsx` with one column per rule set (cells needing human review are filled yellow). Any further columns of the upload are passed through to the output and used as row context (`_row_context`): they are never normalized, but they join the retrieval query and the prompts, which is what lets one document's rules for two different subjects ("Item: gate valve" vs "Item: pump") be told apart. Rows with different context are also kept apart by the consistency and reconciliation passes. The rule sets are computed in parallel; rows inside one rule set are processed sequentially by the LangGraph `StateGraph` (`start_row` → `normalize_row` → `next_row` / `end_node`).

The message is handled by an agent (`modules/agent.py`, `AGENT_PROMPT`): a tool-calling loop (`run_agent`, capped by `MAX_AGENT_STEPS`) over the files of the conversation. The tools are `list_files`, `list_standards`, `inspect_file`, `normalize_file` and `edit_result`; the agent never normalizes anything itself, it decides which file, which standards and which of the user's rules go into a run and calls the pipeline. That is what makes "I forgot a rule, run it again" work without re-uploading, and it generalizes: "the first file", "only that standard", "what is in my file?", "fix row 3".

`modules/workspace.py` holds those files — per `session_id`, in process memory, bounded by count and TTL, nothing on disk. A backend restart (including `--reload` on every code edit) forgets them, which is the price of that choice.

The rules a user states never enter the standards' pipeline — the columns of the documents stay exactly what the documents say. They are a separate pass after it (`run_user_rules_column`), applied to the **recorded** value with the user's rules as the only rule text, landing in one extra column (`USER_RULES_COLUMN`). The agent passes them to `normalize_file` per run. A row whose attribute no rule names (`_adhoc_rules_for_attribute`, same word-wise match as everywhere else) is copied through unchanged, so the column shows the effect of the user's rules and nothing else. The rules live for the run they are passed to and are never written to the knowledge base. A rule about a kind of quantity ("all masses in tonnes") carries `quantity` (a unit) instead of `attribute`: it selects rows by the value's dimensionality (`tools.same_quantity`, pint; a bare number takes the unit of the label), and `_records_quantity` (`QUANTITY_KIND_PROMPT`, cached per attribute) keeps out a class written in a unit's name (`Pressure rating: 300 lbs`). Matched by name, the agent's `attribute: 'Mass'` found none of the `Weight` rows. `normalize_file` reports `rows_matched` per rule, and the agent must say when a rule matched nothing, instead of reporting it as applied.

Before any of that, `prepare_frame()` makes the upload workable: duplicate headers are renamed (`Attribute (2)`), and `Attribute`/`Value` become text — a datasheet keeps sizes as numbers, test dates as dates and blanks as NaN, all of which used to reach `value.strip()` and fail the request. `normalize_table` then never overwrites an existing column of the upload: a result column whose name is taken gets `(2)` appended (`_free_column_name`). On the way out, `_write_excel_with_highlight` strips characters Excel refuses, caps a cell at 32767 characters, and writes a value starting with `=` as text rather than a formula.

Every value column is followed by a column of the same name plus `APPLIED_SUFFIX`, saying what actually fired on that row: the deterministic step that closed it, the clause the model says it applied (the `precondition` field of `SYSTEM_PROMPT1`, which used to be discarded), the post-passes that changed the string, and the guard that rejected an answer. A row nothing applied to says so. It is assembled from facts, not from the model's prose: what the tools did (`_tool_note`), what changed between the record and the result (`_describe_change` — «добавлен пробел», «пересчёт: 10 kV → 10000 V», «разделители: «-» → «~»»), and only the clause numbers the model cited (`_cited_clauses`). Its own explanation was long, in English and sometimes wrong about itself. That is also how a gap in the document itself is reported — including a citation the extraction cannot resolve (`_unresolved_references`: «normalized per 3.1» when the extractor dropped that clause's number, so its text never reaches the model) — «реестр: такого пункта в документе нет», «правила документа дают два разных ответа», «найдены правила разных изделий, контекст строки не уточняет» — instead of the pipeline inventing a decision.

Per row, `start_row` first tries the deterministic path (`apply_deterministic`): excluded attribute → unchanged; exact phrase match; keyword→root; closed-register match. The root step runs before the registers: `Connector size 18` is a designation, not an entry of the connector-type table that a fuzzy attribute match drags it towards. Only what is left goes to the model.

- The register step (`match_closed_register`) takes an exact/near-exact fuzzy match as the code. In the gray zone it asks the model to pick from the full register (`REGISTER_PROMPT`), which answers with a code, `AMBIGUOUS` or `UNMATCHED` — a reworded entry ("Gate, solid wedge") is matched, a genuinely absent one is flagged rather than approximated.
- A code is only ever written into the cell when the wording matches the register entry by word content (`_wording_matches`): word order, commas, hyphens and a bracketed qualifier may differ, an extra or missing word may not. When the entry is merely the closest one ("NPT threaded end" vs "Threaded end"), the recorded value is reproduced as-is and the row is marked for review — approximating a closed register is exactly what the standards forbid. A value listing several items with `;` is matched item by item, so an enumeration is not a wording difference.
- An outcome of the register is worded `pending registration: <value>` / `ambiguous match: <value>` and carries no code: it used to be prefixed with the code of the *nearest* entry, so a cell read `THRD pending registration: Wafer-type, lugged` — the code of a different connection. In an enumeration, one unresolved item makes the whole cell one verdict plus the recorded value, instead of gluing codes and status words together.
- `apply_deterministic` therefore returns `(value, needs_review)`; the flag travels through the graph as `needs_review_flag` and ends up in the `Ambiguous` column that drives the yellow fill.
- When the retrieved groups belong to different subjects (`subjects.json`), `_select_by_subject` keeps only those matching the row context, comparing word by word so that "gate valves" in the tagging matches "gate valve" in the sheet. With no context, or none matching, every group is kept and the row is marked for review — the alternative is deciding between two subjects' rules by coin flip.
- `_document_covers_row()` leaves the column **empty** (and does not mark it — a blank cell says it itself) when the document does not govern the row's item: a file of pumps run against a valve standard gets blank cells, not copies of the record. The decision is not made from `subjects.json` alone: a kind named in the document's scope but carried by no tagged group (a standard that covers control valves without a single group tagged for them) is answered by asking the model against the opening rules (`SCOPE_PROMPT`), cached per document and context.
- Class groups (`RuleSet.class_blocks`) are not searched. `_row_class()` picks the row's class from the row context: by words first, taking the longest class name that matches ("Pressure relief valve", not "Valve"), otherwise with one cached model question. `build_rules_text` inserts only that class's block after the global rules. `_document_covers_row` treats a row whose class has a section in the document as covered: judged from the opening of the document alone, the model had blanked a loudspeaker the document describes.
- `_equipment_kind()` states in the prompt which kind of equipment the row is about when the row context names it by code rather than by word ("Item: GLV-15001"). The pipeline already worked this out for the subject filter; without passing it on, the model picked a row of the document's own per-equipment table at random (a size in cm came out as "0.1 m", the rule for pipe length).
- `expand_references()` then resolves what those rules point at: clause numbers they cite (two levels deep, capped by `MAX_PULLED_CLAUSES`, and only numbers that the clause index actually defines, so decimals inside values are not mistaken for references), and, when the text mentions a table/appendix/register, the document's own entries for this attribute (`_register_lines_for_attribute`). That function returns **two** tables and they are quoted under different headers: phrase→code is a closed list of values ("use an entry from it"), while keyword→root are roots for the NAME of a designation. Merged into one "closed register" block, the roots became answers: a recorded size of `7,62 cm` came back as `NPS 7,62 cm`. The tables live in the extraction artifacts, not in the rule text — without this step a rule like "use the invented root given in Table 1" reaches the model with no Table 1, and 48 of the 62 roots of XYZ STD 205 appear nowhere in the prose it sees.
- `normalize_row` sends the **whole** relevant rule text at once (global rules + `RETRIEVAL_K = 4` retrieved groups; the query is attribute **and** value). Rules are not fed in chunks: incremental feeding anchored the answer on whatever arrived first.
- Each sample is normalize (`SYSTEM_PROMPT1`) + review (`VERIFY_PROMPT`, catches over- and under-application, example leakage, dropped content). `SELF_CONSISTENCY` samples (default 1, override with `NORMALIZER_SAMPLES`) run in parallel and the majority wins; a split vote marks the row for review. Accuracy measured the same with 1, 2 and 3 samples. With the parse-based checks on all the eval sets (712 rows): 1 sample 696 correct, 2 samples 695. One sample costs about 30% fewer calls (2852 against 4095). What a second sample buys is the review mark on a split vote: unmarked wrong answers rose from 8 to 14 with one sample. With two samples a tie goes to the first sample.
- `modules/tools.py` also offers `remove_characters` / `replace_substring`, and the prompt tells the model to carry separator edits out with them rather than retyping the value, so the edit lands on every occurrence. `_partial_separator_edit` then checks the result deterministically: if the same character was edited in some places and left in others ("C-Mn-Si" -> "C-MnSi"), the row is marked for review. The check only runs while the value's own content is unchanged — once it has been replaced by a code, its separators are nothing to compare against.
- Post-passes over the finished column: `_strip_redundant_parenthetical` (drops a parenthetical that only repeats what the code already encodes), `_reconcile_equivalent_rows` (`RECONCILE_PROMPT`, unifies how the rules were *read* for values that mean the same thing — it may only change separators or revert to the recorded value, never reorder content), `_apply_render_template` (re-renders a number to the document's decimals/suffix; `_names_clash` keeps a template of a *different* named attribute away — "nominal length" (m, 1 decimal) must not re-render "Nominal size"), `_canonicalize_formatting` (merges results that differ only in whitespace, and only with a strict majority: on a tie it leaves the rows alone rather than inventing a convention — it used to pick the shortest and so dropped a space the document required), `_align_root_spacing` (a root and its number are joined the way the deterministic path joins them — the model wrote `TRIM8` in one row and `TRIM 12` in the next — unless the document's own example keeps the space: `"150 Class" → "Class 150"` means `Class150` is wrong, whatever other documents do with their roots), `_canonicalize_units` (one spelling of a unit per attribute: `3.000 in` and `11.811 in.` in one column — but only with a strict majority, because the case of a unit is meaningful: `Pa` is a pascal and `PA` is a peta-ampere).
- The checks below do not take strings apart with regexes. `pipeline/parsing.py` asks the model, in a separate cached call with no tools (`PARSE_PROMPT`), what a record or an answer consists of: kind (number, quantity, range, designation, code, text); each number as written, with its unit as a standard pint name, the unit as written and whether a space separates them; the root and number of a designation; the unit named in the attribute label. The call is independent of the normalizing call on purpose, since a parse returned in the same answer could be wrong in agreement with it. Before this, `0.5-inch`, `2 1/2"`, `600#` and `10...20 mm` each needed another regex. Units are compared through pint (`tools.unit_mismatch`, `same_dimension`). A gauge or absolute mark is not in the unit name: the parse returns it separately (`reference`, whatever the spelling — `barg`, `bar(g)`, `kg/cm2g`, `bar abs.`), and `parsing.units_differ` counts it only when both sides carry one (`barg` ≠ `bara`, while `bar`, `barg` and `bar(g)` are one unit). An earlier closed list of five pressure units in the code missed every other spelling. With no parse available, a check rejects and rewrites nothing. The cost is about 50% more model calls per model-handled row, and runs take roughly twice as long.
- `_rejection_reason()` then rejects an answer the rules cannot justify — one question with several checks behind it, each earned by a concrete failure; the row keeps the recorded value and is marked: `_root_invented` (a root whose designation the record does not name — `F51` → `TRIM51`, `PN 100` → `CL100`; it stands down when the attribute label names the designation and the record's letters are part of its number, so a document may define `10K` → `WP10000`), `_root_misapplied` (a root glued to text instead of a number — `TRIM f6a`), and `_unit_relabelled` (the number unchanged while the unit silently became another one — `9.5` under a `, mm` label came back as `9.50 in.`) and `_unit_invented` (a unit in neither the record nor the label — a bare `150` came back as `150.000 in.`, a claim about the quantity rather than its spelling). `_root_misapplied` also covers a root glued to a measurement (`150 MM` → `DN5.906 in`) or to a decimal (`6 IN` → `NPS6.000`): a designation number is a whole number, not a converted length. Units are compared through pint (`tools.unit_mismatch`), never as strings: `in.`, `in` and `inch` are one unit, and `HB minimum` is not a unit at all. `_conversion_of_designation` runs after `_rejection_reason`. When the answer converts the record to another unit of the same dimension (`tools.unit_converted`), it asks once per attribute (`_records_quantity`, `QUANTITY_KIND_PROMPT`, cached) whether the attribute records an amount or a designation. A designation keeps the recorded value and is marked. Without it, `Rating: 800 lbs`, a pressure class, came back as `362.87 kg`. `_strip_added_words` (it removed a word found neither in the record nor in the document's tables — once `A216 WCB` came back as `ASTM A216 WCB`) is still in `guards.py` but is no longer called. It also removed words the document requires (`NPS 4`, `CL 600`, `Trim 12`). With 2 samples, turning it off raised MNT-DN-014 from 80 to 92 of 100 and EMD from 89 to 94, left the other sets unchanged, and no invented words appeared.

- The tool loop (`_invoke_with_tools`) is bounded by `MAX_TOOL_STEPS` and refuses to repeat an identical call, and the tools answer `no change: …` when they would do nothing. Without that, a model that kept asking for `replace_substring('m3/h' → 'm3/h')` looped forever: one row ran for five minutes. When the budget runs out the row keeps the recorded value and is marked.
- `modules/tools.py` gives the model one generic `convert_units(value, from_unit, to_unit, decimals)` built on **pint**. The model reads the record itself and passes it already taken apart (`0.5-inch` → value 0.5, from_unit `inch`; `2 1/2"` → 2.5 inch; a range one bound per call). The code only computes. It used to take the raw string and parse it with regexes (fractions, decimal comma, inch marks, and a hyphen as in `0.5-inch` that pint read as "0.5 minus inch"), and every new way of writing a value needed a new rule. Unit names are pint's, plus the engineering power notation (`mm2`, `m3/h`, `m²`). A gauge or absolute pressure is passed without its mark (`barg` → `bar`), and the model puts the mark back in the answer. Nothing in `tools.py` parses a value string any more. An unknown unit or an impossible conversion answers `cannot convert: …` with the accepted names, and the model fixes the name or gives up — it never makes a number up. There is no fixed list of conversion pairs: with one, the model reached for the nearest pair when its own was missing (it called inch→mm for a value in cm) or converted in its head. Tools are wired into the model via `bind_tools` in `modules/config.py`.
- `modules/system_prompts.py` holds the runtime prompts (`SYSTEM_PROMPT1`, `VERIFY_PROMPT`, `REGISTER_PROMPT`, `RECONCILE_PROMPT`, `SUBJECT_CHOICE_PROMPT`, and the agent's `AGENT_PROMPT`). They must stay document-agnostic: no attribute names, values or phrasings of a particular standard.

### Attribute specification (default normalizer of the API since 2026-10-08)

`pipeline/runner.normalize_table` — what `/process` and the agent's `normalize_file` call — computes a document's column with `spec_runner.run_spec_rule_set` when the document has an `attribute_spec.json`, and with the graph described above (`run_single_rule_set`) otherwise or when `NORMALIZER=legacy`. Same output contract (`Rules_Value`, `Ambiguous`, `Applied`, where `Applied` is the confidence level and its basis); a row whose item the document does not govern stays blank (`_document_covers_row`), as before. The spec path needs the tool-free model (`AppConfig.assistant`). Building a document's spec: `attribute_spec.py` → `spec_verify.py` (an independent model call checks every spec against the rules; a correction is accepted only with a verbatim quote code finds in the text, and only in the spec's own schema) → optionally `spec_check.py`. The general rules are passed whole (`GLOBAL_CHARS = 60000`): cut at 8–12 thousand characters, EMD's rule 7.3 "trailing zeros removed" at character 12 543 reached no step. The exact-form step also looks the record up in the document's own lists (`table_roles.json`), because the model copies long tables into a spec incompletely (one of EMD's three material tables). Measured 2026-10-07, silent errors (wrong and not yellow) per document: EMD 99 rows — spec 87 correct / 3 silent, legacy graph 92 / 6; AVS 102 rows — spec 90 / 5, legacy 89 / 13. Variants tried on the same sets: the model applying the rules alone (B, `llm_runner.py`, `SPEC_MODE=rules`) and a spec whose fields the model chooses itself (C, `attribute_spec_free.py`, `SPEC_MODE=free`) — neither better on both documents.

### Prototype: attribute specification (details)

A replacement for the per-row machinery above (list roles, cards, render templates and most guards), built on one data model per attribute, the way property dictionaries (IEC 61360, ECLASS) describe a property. **Compile once** — `graphs/structured_documents/attribute_spec.py --doc <folder>` writes `attribute_spec.json`: per presentation group a spec with `kind` (`list` | `quantity` | `format` | `text`), `values` (written value + every accepted form, chains through other tables resolved), `closed`, `unit`, `number_pattern` (an ICU/CLDR number pattern, executed by **Babel**: `0.0` shows exactly one decimal, `0.#` rounds to one and drops trailing zeros, `#,##0.00`, `@@@`), `locale` (whose decimal and grouping symbols the document uses: `en`, `ru`, `de` — a decimal comma is the locale, never a comma in the pattern, where it means grouping), `rounding` (`half_up` default, `half_even`, `down`, `up`), `rounding_scope` (`converted` when the document rounds only converted values and keeps a value already in its unit as written), `unit_space`, `number_format` (`fraction` for inch sizes), the document's own `conversions` and `series`, `instructions`, `flag_when`, and `variants` (an attribute written differently per item kind or per kind of value: `Size` of a valve vs a cable). Tables the group's rules cite (or that other sections cite for this attribute, `Canonical value of Table 12.41`) are added to its text. Values and forms are kept only if they appear verbatim in that text. **Check** — `graphs/rag_agent/spec_check.py --doc <folder>` runs each spec on the document's own before → after examples (`rule_cards.json`) and lets the model repair a spec whose examples fail, keeping the repair only if more examples pass. Many "failures" turn out to be noise in the examples (`C-Mn-Si (unchanged)`, a partial transformation `0.25 → 1/4` of the full `1/4" NPT`). **Execute** — `graphs/rag_agent/spec_runner.py` (`SpecRunner(doc, model).run(attribute, value, item)`): the model chooses, code writes. Label → spec: with an item in the row, a model choice even when a spec has the label's exact name — one name is not one field (FG-07: `Length` of gloves is the cuff length, of a bolt the bolt length; taken by name, `12 in` became `304.8 mm` instead of `305 mm`); the choice is among the specs claiming the label by name or alias when there are several, exact name listed first. Without an item, the exact name decides. Otherwise a schema-constrained model choice that sees aliases, the row's item, the document's section for that item kind (`kind="class"` groups) and the value (`Rating: 600#` is a class, `PN40` is not). Variant: model choice from `applies_to`. Every answer carries a confidence level by evidence, the first word of its note. *High*: the basis is a fact code checked — the form is in the document's table, the rule the model cites is verbatim in the text, the model's "same wording" claim holds word for word, or the quantity was converted and written by code. *Medium*: a model judgment with nothing to check it against (an equivalent notation, `300#` = `Class 300`; a `format`/`text` answer) — accepted only if a second, blind call (different prompt, options reversed, first answer not shown) arrives at the same value. *Low* / *disagreed*: yellow, with the proposed value(s) in the note. Code does not judge meaning: a word-content filter that rejected every answer whose words differed from the table entry cut correct equivalents and was removed (`_wording_matches` now only verifies the model's "same wording" claim). `list`: exact form, otherwise a choice constrained to the list values or `UNMATCHED`. `quantity`: the model reads number and unit together with the document's rules (`_read`, `READING_PROMPT`) — how a record is read (a number without a unit is in mm, a decimal comma, a belt code `B75` = inches plus the section's offset) is an open set of rules, not a spec field; every assumption taken from the document rather than the record carries a verbatim quote that code looks up, and one without a found quote sends the row yellow. What the written value must carry besides number and unit (`approx.`, `@ 40 °C`) the reading reports in `keep`, and such a value is written by the model; a character check on the record (`_leftover`) did this before and was removed — without either, `ISO VG 220 base` lost its `@ 40 °C`. A narrow per-case question ("which unit is a bare number in?") read less and gave different answers run to run. Conversion (document factor first, pint otherwise), series, rounding, number pattern and unit are code; a bare number (no unit in the record or in the label) is not converted, and when the spec has a unit the value with that unit goes out yellow as a proposal (`низкая: в записи нет единицы`). The pattern replaced three home-made fields (`decimals`, `max_decimals`, `decimal_separator`, still read from specs compiled before 2026-10-08): the model kept confusing "show N decimals" with "round to N decimals" (`156 kg` → `156.0 kg`, `1250 kW` → `1250.0 kW`). In a pattern these are two spellings, not two readings of one field, and `spec_verify._check_zeros` asks that one question on its own (`ZEROS_CHECK_PROMPT`: show or remove trailing zeros, with a verbatim quote; general rules on zeros apply to every attribute). `number_format.valid_number_pattern` rejects prose and a comma used as a decimal separator in a pattern — the verifier once "fixed" `0.00` to `0,00` for a Russian document, and Babel wrote `0 03 МПа`. Measured 2026-10-08 after the switch: AVS 93/102, 3 silent (was 90 / 5; the rest are text formats, not numbers); STO 23/24 (the one silent row is a Latin `m³` where the document writes Cyrillic `м³`); PLX 27/27; RTE 23/24, 0 silent; WHX 19/23, 0 silent; ICS 21/24, 1 silent (an ambiguity of the synthetic document itself). EMD, re-read 2026-10-08/09 with the caption rule (Ball mounting and the Stellite rows are back) and rebuilt with the pattern: 98/99, the one silent row being the test-file artefact (`=%` became an empty cell) — against 87/99 and 3 silent before, and 92/6 for the legacy graph. The verifier had to be told what `rounding_scope: converted` means: not knowing that the code keeps a value already in the unit as written, it "fixed" patterns to `0.############################` so as not to round such values, which also stopped rounding converted ones (and 28 `#` overflowed Decimal's default precision; `format_number` now raises it). The verifier also sets `rounding_scope` on list attributes; the runner reads it only for quantities. `format` / `text` / unmatched / empty: the model per the spec's instructions and the document's general rules, with a `flag` when the document says to keep and report. Designation roots (`deterministic_rules.json`) are passed to the model, the table winning over a misspelled root in the prose.

Measured 2026-10-05, before the confidence levels and the blind check (they are not measured yet), against the current pipeline (one run each): PLX 27/27 (18), WHX 21/23 (19), RTE 22/24 (23), XYZ `run_eval` 106/108 (107), OGS 108/120 (117), AVS 91/102 (91), HB-15 98/102 (97), DG-07 91/104 (94), PQS 100/108 (100), MNT short 93/100 (93), EMD short 83/99 (93), and 3–4× faster. EMD's gap is largely extraction: it was read by the old 4-bit VLM, which merged the rows of Tables 12.6/12.7. Scoring (from the repo root, one process at a time — several in parallel ran the machine out of memory): `venv2/Scripts/python graphs/rag_agent/eval/spec/score_xyz.py` (the `run_eval` set), `.../score_key.py <doc folder> <input.xlsx> <key.xlsx> "<key column>"` (answer-key sheets), `.../score_expected.py <doc folder> <input.xlsx> <expected.json>` (the synthetic sets of `eval/synthetic/expected`).

### 3. `rag_agent/eval` — regression harness

`graphs/rag_agent/eval/expected.py` holds the expected output of both rule sets for every row of `data/input/test_attributes_api600_new_new.xlsx`, the rows that must (and must not) be marked for review, and the row pairs that must produce byte-identical results. `run_eval.py` runs the pipeline and prints accuracy, mismatches and inconsistent pairs. Rows where the source standard is genuinely ambiguous are documented there.

### Frontend

`client/src` is a minimal create-react-app: `App.js` renders `Layout/ChatPage/ChatPage.jsx`, which composes `Header`, `ChatHistory`, and `MessageInput`. `MessageInput.jsx` posts the message, the last `HISTORY_LIMIT` turns, the picked standards (from `GET /standards`) and the attached file as `multipart/form-data` to `http://localhost:8000/chat` (hardcoded `API_BASE`) via axios, prints the reply and turns the base64 of each returned file into a downloadable attachment. It generates a `session_id` per page load (that is the conversation whose files the backend keeps) and renders every file of the `files` array as an attachment. The send button is rendered by hand (`footer`): the stock one is disabled on an empty input, and a file with no covering text must still be sendable; while a request is in flight it is the library's `LoadingButton`, whose `onCancel` aborts the axios request (the backend, being synchronous, still finishes the run).

## Conventions / gotchas

- CORS on the backend only allows `http://localhost:3000`.
- `structured_documents_graph.py` opens the PDF via a relative path (`../../graphs/structured_documents/data/input/API-600.pdf`) and imports `Settings` via `from graphs.structured_documents.modules...`, so it must be run from the repo root with `-m`.
- The `.env` file (ignored by git) supplies `OPENAI_API_KEY`.
- Several data outputs (e.g. `graphs/rag_agent/data/output/result*.xlsx`) are generated artifacts and should not be committed.
